# 제안서 작성

이 Skill은 승인된 분석을 실행 가능한 제안으로 변환한다. 프레젠테이션을 함께 만들지 않고, 결과를 스스로 승인하지 않는다.

## 승인 게이트

1. `${CLAUDE_PROJECT_DIR}/CLAUDE.md`와 `output/workflow-status.md`를 읽는다.
2. 트렌드 분석 상태가 `approved`인지 확인한다.
3. 리서치 보고서와 트렌드 분석 파일이 모두 존재하는지 확인한다.
4. 승인이나 파일이 없으면 무엇이 필요한지 알리고 중단한다.

## 입력

사용자 요청: `$ARGUMENTS`

- 기본 입력은 `output/02_trend-analysis/trend-analysis.md`다.
- `input/client-brief.md`, `output/01_research/research-report.md`도 함께 읽는다.
- 다른 경로가 지정되면 승인 대상과 일치하는지 확인한다.
- `references/kpi-and-traceability.md`를 읽고 지표와 근거 추적 기준을 적용한다.

## 작성 절차

1. 리서치의 확인된 사실과 트렌드 분석의 해석을 분리해 요약한다.
2. 대상의 현재 상태, 원하는 상태, 핵심 격차를 이용해 문제를 정의한다.
3. 문제와 직접 연결된 목표를 설정한다.
4. 각 목표에 대응하는 핵심 제안을 작성한다.
5. 실행안을 과업, 담당 역할, 입력, 산출물, 완료 조건으로 구체화한다.
6. 일정에 단계와 의사결정 지점을 포함한다.
7. 인력, 도구, 데이터, 예산 등 필요한 자원을 적는다.
8. 위험마다 예방, 발생 시 대응, 담당 역할을 정한다.
9. KPI마다 정의, 기준값, 목표값, 측정 주기, 데이터 출처, 담당을 적는다.
10. 제안 항목을 트렌드와 리서치 출처에 연결하는 근거 추적표를 만든다.

## 근거와 가정

- 입력에 없는 예산, 성과 수치, 일정, 인력 수를 임의로 확정하지 않는다.
- 미확정 값은 `TBD`, `확인 필요`, `가정`으로 표시한다.
- 가정에는 검증 방법과 의사결정 시점을 붙인다.
- 기대 효과는 정량 근거가 있을 때만 숫자로 표현한다.
- 해결책을 먼저 정한 뒤 근거를 끼워 맞추지 않는다.

## 작성

1. `templates/proposal-template.md`의 필수 구조를 사용한다.
2. 경영진과 실무자가 모두 이해할 수 있는 명확한 문장을 쓴다.
3. 전략 이름은 행동과 결과가 드러나는 표현을 사용한다.
4. 제안의 범위 밖 항목과 보류 조건을 숨기지 않는다.

## 저장과 상태

1. 기존 `output/03_proposal/proposal.md`가 있으면 `archive/`에 타임스탬프 이름으로 보존한다.
2. 새 제안서를 `output/03_proposal/proposal.md`에 저장한다.
3. 상태표에서 제안서를 `draft`로 변경한다.
4. 기존 제안서가 변경되었으면 구성안과 실제 PPT를 `stale`로 변경하되 파일은 삭제하지 않는다.

## 완료 전 검사

- 문제, 목표, 제안, 실행안, KPI가 한 흐름으로 연결되는가?
- 모든 핵심 제안의 근거를 추적할 수 있는가?
- 일정, 역할, 자원, 위험 대응이 있는가?
- 숫자와 예산을 임의로 만들지 않았는가?
- 의사결정자가 승인하거나 보완할 항목이 분명한가?

완료 후 생성 파일, 핵심 제안 3개 이내, 미확정 항목, 승인 대상, 다음 명령을 보고하고 멈춘다.
